# ADR-0015: Storefront architecture: a BFF on Next.js 16, sessions in our own cookies

Status: Accepted (2026-11-19)

## Context
The storefront (PLAN M4) must look like Saleor's Paper (`../saleor-storefront`, ADR-0008) but run
on our API. Paper relies on things we don't have: Saleor channels, JWT access/refresh tokens, an
app token for reading orders, and webhooks for cache invalidation. Our API has opaque DB sessions
(ADR-0006), one channel (ADR-0005) and MNT money (ADR-0013). Owner decisions (2026-11-19): URLs
`/{locale}/…` with `mn` (default) and `en`; dummy payments only for now; deployed on the bare
domain `dino-craft.lol`, next to `admin.dino-craft.lol`.

## Decision

**Stack** (Paper's versions, pinned): Next.js 16 App Router with `cacheComponents`, React 19,
Tailwind 3.4, next-intl, Radix primitives, lucide-react, clsx. Biome as in the rest of the repo, not
Paper's ESLint. No urql and no GraphQL client in the browser.

**Backend for frontend (BFF).** Only the Next.js server talks to the API, through one module
`src/lib/api/` (`server-only`), using documents generated by graphql-codegen's client preset from
`apps/api/schema.graphql`. Server Components read; Server Actions and route handlers write. The
storefront uses only public and customer operations, and holds no staff credentials (ARCHITECTURE §10).

**Customer session.** `/api/auth/login` (a route handler) calls `tokenCreate` server-side, reads
the session token from the API's `Set-Cookie` response header, and stores it in our own cookie
`session` (`HttpOnly; Secure; SameSite=Lax; Path=/`, same lifetime as the API session). Each API call
sends it as `Authorization: Bearer`, which ADR-0006 already allows. Logout calls `logout` and clears
the cookie. The browser therefore never sees the token, and the API needs no change.

**Checkout.** The checkout token is a second HttpOnly cookie, `checkout`. Cart mutations are
Server Actions; there is one cart per browser, attached to the customer at login
(`checkoutCustomerAttach`). The steps are `?step=contact|shipping|payment` on one route, as in
Paper. Payment goes through a small provider registry with one entry, `dummy`, today. Guests see
their order on `/{locale}/order/{token}` through the guest order lookup (PLAN M15.3), never
through a staff token.

**Client IP.** Login throttling keys on the client address. The storefront passes the shopper's
address on to the API in `X-Forwarded-For`, and the API trusts it only from the storefront's
network path. The exact setup is fixed and tested in PLAN M4.7, before login ships.

**Routing and strings.** The `/{locale}` segment is handled by next-intl middleware: `/`
redirects to `/mn`, and an unknown locale returns 404. UI strings live in `messages/{mn,en}.json`.
Catalog content is not translated (the API has no translations). Money and dates are formatted with
`@commerce/contracts` and `Intl`.

**Caching.** Catalog reads (products, categories, collections, menus, pages) are `"use cache"`
functions with `cacheTag`s per entity and a `catalog` `cacheLife` profile: stale 1 minute,
revalidate 2 minutes, expire 1 day. With no webhooks, staff edits appear within about two minutes.
Cart, checkout, account and every request that reads cookies are dynamic. On-demand revalidation
(the API job outbox calling a signed `/api/revalidate`) is deferred to a later milestone. The
default in-process cache is fine for one instance; more instances need a shared cache handler first.

**Images.** `next/image` with an explicit `remotePatterns` allowlist (the API host and the S3
media host), WebP, and Paper's size ladders. No wildcard host in production.

**Deployment.** `output: "standalone"` in its own Docker target, run as a third service on the
existing EC2 host behind nginx at `dino-craft.lol`. It reaches the API over the internal network
(`API_URL`, server-only env).

**Code layout** mirrors Paper so adapted files are easy to compare: `src/app`, `src/ui/{atoms,
components}`, `src/checkout`, `src/lib`, `src/styles/brand.css`, `messages/`.

## Alternatives
- **The browser calls the API directly** (cookie on a shared parent domain): no BFF, but the API
  cookie, CORS and CSRF rules would have to cover a public site, and throttling would see the
  shopper's IP directly. Rejected: it leaks more surface for no gain once the BFF exists.
- **Return the session token in the `tokenCreate` body** (as Saleor does): simpler parsing, but
  it would expose the token to the dashboard's JavaScript as well. Rejected.
- **Paper's channel segment `/{locale}/{channel}/`**: no value with one channel (ADR-0005).
- **Webhook-driven revalidation now**: fresher, but needs a webhook system the API doesn't have.

## Consequences
- + The token never reaches browser JavaScript; there is no client GraphQL bundle; SEO works by default.
- + No API change is needed for sessions or carts.
- − Every request costs one extra hop (browser → Next → API), and session validation still costs
  one DB lookup per request (ADR-0006).
- − Parsing `Set-Cookie` couples the BFF to the API's cookie name. A contract test pins it.
- − Up to about two minutes of staleness for catalog edits, until on-demand revalidation lands.
